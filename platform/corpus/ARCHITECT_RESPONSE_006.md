## D31 — RULING: the activation pass, executed by ceremony, authorized by DEC-0003

**The shape.** ONT-060's table already contains the activation logic:
ratified → active is triggered by *binding completeness* — claims need
an active rule binding them, controls need a resolving implementation,
and "others" (rules, enforcements, principles, restrictions-as-claims
follow the claim rule) activate on ratification. So the decision's job
is only to move the extracted corpus proposed → ratified; **eligibility
for active is computed, not decreed.** A blanket "everything active"
would violate ONT-033 the moment it touched a control whose suite does
not yet exist — the meters must be allowed to read the honest partial
state.

**The mechanics** (SPEC-0111/0112):

1. `tools/enact.py` — the ceremony tool. Given a decision ID: applies
   its effects mechanically (state transitions, version bumps per the
   ratification conventions now on record, shared timestamp), then
   computes ONT-060 activation eligibility across the corpus and
   re-versions eligible atoms ratified → active in the same pass.
   Ineligible atoms remain `ratified` and become visible meter lines:
   *ratified controls without resolving implementations*, *ratified
   claims without active rules*. Output is a staged working tree plus a
   dry-run report; the tool never commits — the owner's PR-and-merge
   remains the signature, per the D22 pattern.
2. `DEC-0003` — "Activate the extracted rule set." Its effects block is
   **generated by the tool** against the live corpus at a named digest
   (enumeration, since the ref grammar has no wildcards) and then
   human-ratified — machine-written, owner-signed, which is the correct
   division of labor this whole system argues for. Scope: the
   REQUIREMENTS_REGISTER, CONTROLS, ENFORCEMENT_RULES atom sets, plus
   the story-scoped acceptance SPECs of *closed* stories
   (open stories' acceptance stays proposed until their work merges —
   acceptance activating before its story completes would be a claim
   ahead of its implementation).
3. After the owner merges DEC-0003's enactment: `dangling_claims`,
   `rules_without_passing_evidence`, and the ratified-but-inactive
   lines all become live launch-readiness numbers, and PA-022's
   done-test means what it says.

**Sequencing:** SPEC-0111/0112 execute **before STORY-0002** — the
spawn gate should refuse and admit under active law, not proposed
suggestions, and the risky hop deserves live meters.

## D33 — RULING: P5's tree is fixture, not implementation

SPEC-0108's "no second chain walk" static check is scoped to **logic,
not test data**: no non-test module may implement predicate evaluation,
caveat union, or chain verification; test modules may *construct*
credential trees and revocation sets as fixtures, but every verdict in
P1–P6 must come from `chainverify` — the citizen implementation is the
only oracle for outcomes. P5's expected values derive legitimately from
fixture-construction knowledge (the test knows which nodes are
descendants because the test built the tree — that is data it authored,
not a walk it reimplemented). What would violate the check: any test
helper that computes verification results independently to compare
against chainverify — a shadow oracle is a second implementation
wearing a test's clothes. Static check wording: outside `base/l0/`,
no function may evaluate caveat predicates or walk credential chains;
fixture builders that only construct inputs are exempt.
